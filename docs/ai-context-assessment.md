# API Wiki 与 Air 协作评估

核对日期：2026-10-18。本文记录路线图第 14、15 项的评估与待验工作流，不代表 Wiki、Air 或 MCP 集成已经通过验收。当前实现状态以[路线图](roadmap.md)和各 change 的 verification 为准。

## 决策

先用第 11 项项目内 Markdown 形成可导航的 API Reference；继续在同一个插件内复用解析与导出，不拆独立 Wiki 插件。Air 先作为这些普通文件的消费者；Doc View 不注册 ACP agent，不代管模型、账户、会话或额度。正式 MCP 查询工具必须等待第 12 项真实 IDE 准入验证。

这与全仓库知识 Wiki 的目标不同。Qoder 官方 Repo Wiki 描述了仓库结构/实现分析、增量更新及人工编辑保护，生成与更新会消费其 Credits；这些是独立产品能力，不能从 API 文档生成直接推导为已支持。本轮没有调用 Qoder 或创建付费生成任务。[Qoder Repo Wiki](https://docs.qoder.com/user-guide/repo-wiki)

## 轻量 API Wiki 的最小验证

第 11 项已经定义逐接口页面、稳定身份、模块/签名索引和源码链接。第 14 项应先以这些产物验证以下阅读任务，再决定是否增加模型目录：

| 阅读任务 | 需要的事实 | 验收标准 |
| --- | --- | --- |
| 查找某模块接口 | 当前导出索引中的模块、完整签名和页面链接 | 能唯一定位；同名重载和跨模块接口不混淆。 |
| 查看请求与响应 | 对应接口页的当前模板正文及来源链接 | 能说明输入/输出；模板省略的信息明确为未提供。 |
| 回到实现核实 | 项目相对源码链接 | 链接落到当前工作树源码，不包含本机绝对路径。 |
| 判断是否需要重新生成 | 当前源码与已导出快照的实际差异 | 不把磁盘快照当作实时事实；重新导出后核对变化。 |
| 维护补充说明 | 用户独立编写的概览页，与受管理 API 页的链接 | 人工说明与接口数据可共同阅读，重导出不覆盖手写内容。 |

模型关系当前仍由每份接口正文展示。若实测出现“多个 API 复用同一 DTO，无法定位其字段说明”的问题，再单独定义模型身份、去重、反向引用及输出 contract；不从 display name 猜模型身份，也不重复解析 Java。模块概览只列可证实的接口事实，不自动编写架构或业务结论。

第 14 项已有单模块索引查找、接口页阅读、重载区分及 Document/Source 导航的原生证据；多模块导航仍待补。以上属于轻量 API Reference 的局部阅读验证，不代表 Wiki 可用性整体验收完成。当前未完成项见[路线图](roadmap.md)与[本轮验证记录](validation-2026-10-20.md)，细节保留在对应 change 的 verification。

## Air 的可用入口与边界

Air 是运行和审阅 coding agents 的 IDE 工作区。官方当前说明 2026.2 通过 Marketplace 安装，2026.3 EAP 随 IDE 提供；这不证明 Doc View 的最低平台 2026.1 支持 Air。模型与授权沿用具体 agent/provider 的能力，本轮不安装 agent、不切换授权来源、不启用 Credits。[Air 概览](https://www.jetbrains.com/help/air-ides/air-overview.html)

官方自定义 ACP 配置提供 `use_idea_mcp` 和 `use_custom_mcp`。这只说明 Air 存在工具通道，不能证明第三方 Doc View 工具可被发现、调用或安全取消；相关验证必须在精确 IDE/Air/agent 版本上执行。[Agent 管理与 ACP 配置](https://www.jetbrains.com/help/air-ides/air-manage-agents.html)

| 工作流 | 当前结论 | 下一步条件 |
| --- | --- | --- |
| Air 中的 agent 读取项目 Markdown | 普通文件方案具备可接入条件，实际读取未验 | 第 11 项产物通过；已登录且获授权的 agent；可操作的原生 IDE。 |
| Air 调用 Doc View MCP 工具 | 未实现、未验 | 第 12 项真实服务/生命周期门禁通过后，完成第 13 项。 |
| 自建 ACP agent 或会话面板 | 当前没有独立需求 | 暂不实施，继续使用 IDE/Air 的既有界面。 |
| 宣称减少 token 或提升回答准确率 | 无实测依据 | 同一固定任务与来源对照后再报告；不预设收益。 |

## 可执行的只读验收流程

前提：Mac 已解锁，隔离 IDEA/Air 与已有订阅授权可用，第 11 项通过自动门禁；使用专用 `/Users/liuzhihang/workspace/doc-demo` 的虚构接口。若缺任何账户或环境，只记录缺口，不代填账户、不升级计划或改用 Credits。

1. 记录 IDEA build、Air 版本、agent 和授权来源类型；记录当前源码/导出快照身份，不保存 token 或请求原文中的私有数据。
2. 从 Doc View 导出项目文档，先手工打开索引与源码链接，确认当前输入可读。
3. 在已有 agent 会话提交下面的只读任务；不接受修改源码、上传文档或联网请求作为验收的一部分。
4. 将回答中的每个签名、必填字段和来源链接与生成页及源码核对，记录遗漏、错误与无法确定的信息。
5. 修改一个专用测试接口并重新导出，再做同一查询；确认结果引用新内容。未重新导出时，应明确当前文件仅为旧快照，不宣称实时索引。
6. 若后续 MCP 门禁已通过，再单独测试工具发现、正确 project、取消和关闭；文件读取成功不能代替工具验收。

可复制任务：

```text
只读检查当前项目的 docs/doc-view/index.md。找出指定模块下的目标接口，
区分同名重载，列出完整方法签名、请求参数、必填规则和响应类型。
逐项引用实际读取的接口文档路径与源码路径；文档省略或源码无法确认的信息
明确标记未知。不要修改任何文件、运行代码、上传内容或调用远程平台。
```

本评估当时仅完成官方资料核对与工作流设计；未发起 Air 测试会话，因此真实阅读、回答准确性、费用路径和 MCP 协作仍没有本项目的验收证据。后续若环境和账户可用，按上方只读流程单独验证，不以普通 Markdown 可读或探针通过替代协作验收。

## 历史文档导入与查看（路线图 17）

当前不新增独立 Markdown 查看器。项目已有 `CustomFileUtils.open` 经 `FileEditorManager.openFile` 打开 Markdown 的路径；第 11 项也验证了新导出文件可在 IDE 原生搜索。单纯再做一个阅读面板，尚没有证明能解决新的阅读问题。这里是路线判断，不代表历史快照或差异阅读已实现；第 11/14 项未完成场景见[路线图](roadmap.md)。

有价值的候选是按稳定接口身份比较历史快照与当前源码，而不是把任意 Markdown 猜测还原成 API。`ProjectDocumentPage`/`ProjectDocumentSnapshot` 已是不带 PSI 的输出数据；核心 `DocView`、`Body`、`Param` 仍持有 PSI，不可直接作为历史导入模型。

先完成第 11 项和上面的五项阅读验证。只有实际缺口落在历史目录导航或文档差异时，才单独建立 `doc-import-viewer` change；最小范围为只读识别当前 Doc View v1 marker 管理的索引/页面，用 identity 和文本比较，继续复用原生 Markdown 编辑器。无 marker 的普通或旧 Markdown、外部平台格式和损坏页面明确不作为可还原的接口数据，不自动写回、转换或清理。该候选不会提前加入第 11 项导出实现。
